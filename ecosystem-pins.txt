# serez-ecosystem-pins/1
# The official packages the ecosystem canary runs as a CI gate, as
# `<package>\t<commit>`.
#
# WHY PINNED
#
# DEC-M10-001 makes the canary a blocking gate: if a change here breaks an
# official package, CI fails. §7A's objection to running it per-commit was that
# it "makes every PR's result depend on repositories this one does not control,
# which is how a compatibility signal turns into flakiness". A pin answers that:
# the gate reads a fixed commit of each package, so the only thing that can turn
# it red is a change *in this repository*, which is what a gate is for.
#
# It is also what makes the signal readable. A red gate means "this change broke
# serez-ui at this commit" and never "someone pushed to serez-ui an hour ago".
#
# THE OTHER HALF
#
# A pin goes stale, and a stale pin is a gate that stops testing the packages as
# they actually are. `.github/workflows/ecosystem-daily.yml` runs the same canary
# against each package's **default branch**, once a day, and cannot block a PR.
# The gate asks "did this change break the packages as pinned?"; the daily run
# asks "have the packages moved away from the pins?". They are different
# questions and neither replaces the other.
#
# UPDATING
#
# Move a pin deliberately, in its own commit, with the canary green at the new
# commit. A pin bumped in the same change as a language fix hides which of the
# two made the suite pass.
